Deterministic triage is a routing pattern where every classification decision is made by rule-based code before any LLM agent fires. Instead of passing a raw event to an agent and asking it to decide what the pipeline should do next, you run a set of typed detectors against the structured input and produce a routing manifest. The orchestrator reads that manifest and builds an execution plan. Zero LLM, zero non-determinism — and every routing decision is a deterministic function of the input.

## When to use it

Use deterministic triage when:

- **The routing decision is the most consequential step** — a wrong route propagates through every downstream stage, compounding the error across agents, content, and communications
- **The input is structured** — typed fields, enumerations, and identifiable patterns give your detectors reliable signals to operate on
- **You need auditable, reproducible decisions** — every routing decision should be traceable to the exact detector logic and input that produced it
- **The cost of a non-deterministic routing error is high** — unnecessary escalation costs a few seconds of human review; a missed escalation sends a low-quality signal through the full pipeline

Do not use deterministic triage when classification genuinely requires reading and understanding unstructured natural language that cannot be reduced to field matching or pattern rules. In that case, a bounded LLM classifier with a confidence threshold is the right approach.

## Detector design principles

Well-designed detectors share four properties:

- **One responsibility per detector.** Each detector classifies one dimension of the input. A detector that classifies both change type and audience is two detectors collapsed into one — split them. Single-responsibility detectors are independently testable and independently updatable.

- **Typed output values.** Detector outputs are enumerations, not free text. `new_feature | enhancement | deprecation | fix` — not "this appears to be a new feature addition." Typed outputs make the routing manifest machine-readable and eliminate the need for downstream agents to interpret natural language routing signals.

- **`uncertain` is a valid output.** For binary trigger decisions — does this event require a communications message? — `uncertain` should be a first-class output alongside `required` and `not_required`. Forcing a binary answer on genuinely ambiguous inputs produces confident wrong answers. `uncertain` routes the decision to a confidence-gating step rather than silently making the wrong call.

- **Conservative on escalation.** Your escalation detector should err toward escalating. The cost of an unnecessary escalation is a human spending thirty seconds reviewing a run that didn't need it. The cost of a missed escalation is a low-quality signal reaching the approval gate as a bad proposal. Asymmetric costs justify a conservative escalation threshold.

## Routing manifest output

The triage layer assembles all detector outputs into a single structured routing manifest before passing control to the orchestrator:

```json
{
  "manifest_version": "1.4.0",
  "change_type": "new_feature",
  "scope": "cross_product",
  "audience": "client",
  "urgency": "expedited",
  "notify_trigger": "required",
  "content_trigger": "required",
  "review_trigger": "required",
  "escalation_trigger": "proceed"
}
```

The `manifest_version` field is not optional. When detector logic changes — even a small threshold adjustment — you increment the version. Every historical routing decision is then traceable back to the exact detector version that produced it. Without versioning, debugging unexpected pipeline behaviour after a detector update becomes a reconstruction exercise rather than a lookup.

Validate the manifest against a schema before passing it to the orchestrator. A manifest with missing or malformed fields should fail loudly at the triage layer, not silently produce unexpected behaviour two stages downstream.

## Testing strategy

A well-tested triage layer gives you high confidence that routing decisions are correct before you run a single agent. Good coverage includes:

- **Unit tests per rule path** — one test for each explicit branch in each detector
- **Boundary tests** — inputs at threshold values and edge-case patterns that sit on the boundary between two output values
- **Negative tests** — inputs that should *not* trigger a given classification confirm that your detectors aren't over-firing
- **Regression tests for historical edge cases** — real inputs that caused routing errors in production, added to the suite before the detector was fixed

<Tip>
When a real input causes a detector to misclassify, add it as a regression test before fixing the detector. Your test suite grows with your pipeline's operational history.
</Tip>
