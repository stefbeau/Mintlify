Quality Review is the final automated check before approved content enters your knowledge base. It runs after you approve content at the Human Approval Gate — evaluating exactly what you approved, not an earlier draft. Three sub-agents run concurrently, each responsible for one rule category. Their findings are consolidated into a structured payload that you can act on or override before publication proceeds.

## Rule categories

The Quality Review stage applies 77 rules across three categories.

| Category | Rules | What it checks |
|----------|-------|----------------|
| **Prose** | 39 | Sentence structure, clarity, active voice, concision |
| **Style** | 19 | Tone, register, formatting conventions, heading structure |
| **Terminology** | 19 | Approved terms, prohibited terms, consistency, capitalisation |

Each rule has an ID (for example, `PROSE_014`, `TERM_007`) that appears in the findings payload. Rule IDs make findings traceable and auditable — you can look up exactly what a rule checks and how often it has fired across your run history.

## Parallel evaluation

The three sub-agents run concurrently. Each receives only its own rule set and the approved content to evaluate — they do not share context or interact with each other.

```
Approved content
      │
      ├──▶ Prose sub-agent (39 rules)    ──▶ Prose findings
      ├──▶ Style sub-agent (19 rules)    ──▶ Style findings
      └──▶ Terminology sub-agent (19 rules) ──▶ Terminology findings
                                                      │
                                               Consolidation
                                                      │
                                          Findings payload
```

Running the three sub-agents in parallel reduces Quality Review latency to the duration of a single LLM call rather than three sequential calls.

## The findings payload

The Quality Review stage produces a structured findings payload for each page evaluated.

```json
{
  "page_id": "authentication/api-keys",
  "findings": [
    {
      "rule_id": "PROSE_014",
      "category": "prose",
      "severity": "warning",
      "location": "paragraph_2_sentence_3",
      "description": "Passive voice construction",
      "current_text": "Keys are generated by the system.",
      "suggested_text": "The system generates keys automatically.",
      "confidence": 0.91
    }
  ],
  "summary": { "critical": 0, "warning": 1, "info": 2 }
}
```

Each finding includes the rule that fired, its category, a severity level (`critical` / `warning` / `info`), the precise location in the content, the current text, a suggested correction, and a confidence score. Findings are specific enough to act on directly — you always know exactly what to change and where.

## Acting on findings

You can act on any finding or override it. Both actions are logged as part of the run record. Critical findings are surfaced prominently — they appear at the top of the findings list and are highlighted in the run summary.

If you override a finding, your decision is recorded alongside the rule ID. This data feeds into the pipeline's health metrics, giving you visibility into which rules are frequently overridden and may need recalibration.

<Note>
Quality Review runs after your approval, not before. It evaluates the content you actually approved — not a draft that you might have edited. This ensures the final quality check reflects the final content, not an intermediate version.
</Note>
